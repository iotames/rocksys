# 计划目录工作宪法（智能体深度自主工作）

> 本文是宪法层：只定目标、原则与边界，不为任何特例而设。文中一切命令、路径、目录名皆为**示例**，临场按当前环境取等价手段。
> 层级与裁决：仓库法（AGENTS.md）＞ 本宪法 ＞ 项目总纲与 STEP。冲突时上位优先；本宪法只补充工作流，不重复仓库法内容。

## 0. 一条公理，三条推论

**公理：智能体的会话记忆易失，工程实施长周期。** 因此一切状态必须当场落盘为仓库内文档——"当前进度"是可从磁盘重建的事实，不是任何大脑里的记忆；会话中的口头约定、"记得待会儿要改什么"，一律视为已丢失。断点后的唯一事故现场依据 = 改到一半的代码 + 保持进度的文档，两者之外的一切视为不存在。本文全部机制由此推出。

- **推论一（写给失忆者）**：每份文档假设读者是明天失忆的接手者——决策带理由、现状带证据（代码位置）、动作可勾选、验证带命令。凡"我当时知道就行"的信息必须落到纸面。
- **推论二（机器判定优先）**：测试、构建、锚点检索是机器可判定的事实，人眼读码仅作兜底且只限存疑部分。
- **推论三（代码即最终事实）**：文档与代码可能不一致，不猜谁对——先机器判定裁决，裁决不了以代码为准并立即修文档。文档与代码不符比没有文档更毒。

**适用域**：中大型功能开发（多模块、数据层变更、多轮设计决策、跨会话周期）；小改动直接做，不建计划。**单写者假设**：同一时刻仅一个执行者按总纲推进，多人/多智能体并发须先由人类切分。

## 1. 文档体系：一项目四件，各层只答一层的问题

| 文档 | 位置（示例） | 回答的问题 | 生命周期 |
|---|---|---|---|
| 设计文档 `<项目>_PLAN.md` | 开发期 `docs/`，完成后迁归档目录 | **为什么这么做**：现状结论、决策表、设计方案、验收与变更记录 | 长期归档 |
| 总纲 `TODO.md` | 计划目录根部 | **现在做什么、做到哪**：断点续传协议、状态总表、红线摘录、进度日志 | 全部验收后删 |
| 步骤 `STEPn_*.md` | `docs/plan/<项目>/` | **这一步怎么做**：清单、验证、回填区 | 随总纲删 |
| 临时决策 `DECISIONS_TEMP.md` | `docs/plan/<项目>/` | **人类不在场时的重大拍板**：五要素记录 | 验收审查后删 |

冲突处理：**顺序以总纲为准，理由以设计文档为准，细节以步骤文档为准**；STEP 头部状态行与总表状态冲突时，以总表为准并当场修正。接手者按需读层，不必全读；归档目录仅作人类历史查阅，执行与续传不依赖它。总纲可合并多项目为一张总表；某项目归档后即移除其行，表空后删总纲。

## 2. 生命周期：五阶段

1. **现状排查**：先诊断后开方。现有实现路径、数据来源、既有痛点（带代码位置）、约束条件写入设计文档——设计质量取决于排查深度。
2. **设计定稿（开工前唯一强制请示点；事后关口：验收呈报、归档确认）**：四块——① 现状结论（带证据）；② 已确认决策表（决策点｜结论｜理由；用户每拍板一次落档一行，这是后续任何智能体理解"为什么"的唯一权威来源，防同一问题反复横跳。**决策表只追加不覆盖**：需求变更或前提被证伪时追加新行、旧行标注"被取代"，不静默改写）；③ 设计方案（细化到文件/端点/字段级，不写实施顺序——顺序是总纲的事）；④ 验收标准（怎么算做完：命令/界面操作/明确不做的边界——没有它，终验只能证明"造的能跑"，证明不了"造的是要的"）。**经用户认可才能开工**，同一关口确认 git 破例授权及其范围（§3.6）。此后常规事务不再请示。
3. **拆步建纲**（自主，无需请示）：一步 = 一个可独立验证的交付切片（能跑一次本步验证收口；过大则断点重做面大，过细则管理成本高）。按依赖关系排序，被依赖的地基先行（示例：数据层先于依赖它的端点）。按 §4 模板建总纲与 STEP。
4. **自动执行**：从总纲断点续传协议开始按序执行，铁律见 §3。
5. **验收归档**：见 §5。

## 3. 执行铁律（每条附一句理由；规则未覆盖的边界，按理由外推）

1. **落盘优先**：每步循环 = 读状态 → 接手核实 → 实施 → 勾选 → 验证 → 改状态 → 记日志。清单完成一项，勾选一项，立即保存；状态每迁移一次，立即回总表更新并追加一行进度日志；发现偏差、产生新决策、试错放弃某方案——先写回填区再继续。持久化粒度 = 最大重做量，中断随时可能发生在任意两条动作之间；长命令执行前后与任务切换间隙，随手校对锚点清单与回填区为最新。实施中改名/改路径的偏差，随手同步锚点清单与接手核实命令——恒红的核实命令会诱导接手者重做完好代码。
2. **勾选 ≠ 验证**：`[x]` 只表示动作落地；`✓` 必须紧跟一次真实执行的验证命令，写不出命令名就没有 ✓，无独立验证手段的项不标、由步骤级验证统一兜底；「已实施」只由本步验证全过授予。记号混用则信任链失效——总表是接手者信任的根。打回（后续步骤破坏已实施步骤）：勾选保留、状态回退、被破坏项写入回填区；其下游已实施步骤重跑各自核实命令，不绿者连锁打回——打回不重做，只补被破坏面。
3. **核实走机器判定**：优先级 = 跑该步预写的接手核实命令（必须无副作用、可重复执行）＞ 按锚点检索定位缺口 ＞ 人眼读码（仅限前两者失效时的存疑部分）。核实全成本 = 一条命令，仅在不绿时再加每锚点一次检索——必须远小于重做成本；凡能用测试表达的交付就为它写测试——质量保障与断点续传，一份投入两处收益。
4. **顺序即依赖**：不跳步、不并行；受阻时转向总表中不依赖它的步骤是唯一例外（须在总表标注）。某步受阻：回填原因与已试方案，状态保持「实施中」；同一验证连续 3 次失败即按受阻处理，防无人值守下的无限修复循环；若受阻使后续步骤全部失去依赖，停止执行、落盘现状、等待人类。
5. **重大决策宁简勿繁**：触发（同时满足）——设计/架构量级（数据结构、接口契约、模块划分、依赖引入、既有行为改变、不可逆动作如破坏性迁移/批量删除等）＋ 超出设计文档范围 ＋ 人类不在场（判定：深度自主指令生效后未再收到人类输入；收到任何新的人类消息即恢复请示默认态）。触发即先按 §4.3 五要素落档再继续；日常小取舍（命名、内部拆分、文案微调）直接做，不落档。临场一律选能满足需求的最简方案，复杂化（新增抽象层、引入依赖、多出并行机制）必须写出"不加不可"的理由——简单方案被推翻返工面可控，复杂方案被推翻是重构。**停机线**：决策触及决策表中用户已拍板的条目时，停止该方向实施（仅转不冲突的步骤），落盘等待人类——自主裁量权不能覆盖用户拍板权。**前向传播**：决策落档后当场检查未执行 STEP 是否受影响并修订或标注失效点——续传协议只核实"做没做"，不核实"设计还成不成立"。判断不了算不算重大，按重大处理：多写一条记录的成本远小于漏记。
6. **git 破例授权**（仅当用户在阶段 2 明示授予并圈定范围；否则默认"提交等确认"）：一个 STEP 验证通过即提交，提交历史成为断点续传的辅助事实源；提交信息照仓库规范（未覆盖时兜底：单行摘要直述做了什么＋验证结果）；push 前全量测试与静态检查必须通过；禁止 force push、禁止改写已推送历史；授权范围外的分支/远端照常请示。破例只豁免"要不要问"，不豁免其他确认关口（定稿、归档等照常请示）。

## 4. 模板（字段即契约，新建照抄）

### 4.1 总纲 TODO.md

```markdown
# 执行总纲

项目状态：进行中        ← 进行中 / 待人类验收 / 等待人类（多项目合表时逐项目标注）

## §0 断点续传（接手者从这里开始）
1. 读项目状态行与 §1 总表（多项目合表时逐项目判定，某项目完结不阻塞其余「进行中」项目的续传）：
   - 某项目全部步骤「已实施」→ 该项目终验与呈报未做则先做（宪法 §5），改其项目状态「待人类验收」，此后该项目停止一切实施动作（归档删除与新开工均须人类确认）；
   - 某项目状态为「待人类验收/等待人类」→ 该项目不实施任何动作，向用户呈报等待点；
2. 定位第一个非「已实施」的步骤；其状态含受阻标注时，读该 STEP 回填区受阻记录，未解除则转向总表中下一个不依赖它的步骤（多项目合表时跨项目同理）；
3. 若为「实施中」，先跑该 STEP 验证节预写的接手核实命令（无副作用、可重复执行）：
   - 通过 = 退出码 0 且确有本步测试被执行（防空跑假绿）→ 已完成部分完好：仍有未勾选项则从首个未勾选项继续，禁止重做；已全勾则补跑本步完整验证，通过即改「已实施」收口；
   - 不通过 → 按该 STEP 回填区锚点清单逐个定位，只补缺口；
   - 仍裁决不了 → 以代码为准，修正文档；
4. 若为「待实施」但锚点检索已有产物命中（中断发生在动作落地后、勾选保存前）→ 先核实产物再续做，禁止从零重写覆盖现场；
5. 严禁凭会话记忆做任何实施判断。

## §1 状态总表（状态列可带标注，如「实施中(受阻→STEP5)」）
| # | STEP | 内容 | 状态 |
|---|------|------|------|
| 1 | <项目>/STEP1_xxx.md | …… | 待实施 |

## §2 执行期红线（自仓库法摘录，冲突时以仓库法原文为准）
- ……（示例：构建/测试命令约定、运行目录约定、提示组件规范、文档同步清单）
- git 提交：本次任务【适用/不适用】破例授权，见宪法 §3.6。

## §3 进度日志（一行一事）
| 日期 | 执行者 | STEP | 结果 |
```

### 4.2 步骤 STEPn_*.md

```markdown
# STEPn：<交付物一句话>

状态：待实施        ← 三态：待实施 / 实施中 / 已实施（仅验证全过后可置「已实施」；权威状态 = 总纲 §1，本行仅视图）

## 目标
……

## 改动文件清单
- ……

## 实施步骤（完成一项立即勾选保存；粒度到不可再分的动作）
- [ ] ……
- [x] <动作> ✓（<验证命令>，通过）    ← 项级验证通过时的完整形态：✓ 必须紧跟真实执行的验证命令，无独立验证手段不标

## 验证
- 接手核实命令（拆步时预写；无副作用、可重复执行；断点后一条命令自证已完成部分完好）：
  <示例：go test ./<本步改动包>/ -run '本步测试函数'>
- 本步完整验证（勾选＝该项验证通过；按需含受影响面的全量回归）：
  - [ ] <命令 / 界面操作……>

## 完成标准
- ……

## 实施回填区
### 产物锚点清单（拆步时预写，实施中随手更正；改名同步更新）
- 新增文件：<路径>
- 新增函数/类型/端点/配置项：<名>
- 新增测试：<测试函数名>
### 偏差与现场记录
- <设计与现实的偏差、试过放弃的方案、阻塞原因——先写这里再继续动手>
```

### 4.3 临时决策 DECISIONS_TEMP.md（首次遇到需记录的决策时创建，不预建空文件）

```markdown
## D1：<决策点一句话>（日期 · STEPn 实施中发现）
- 触发问题：实施到哪一步、碰到什么设计文档没预见的状况、为什么绕不开
- 备选方案：至少两案，各自的代价一句话
- 选择与理由：选了哪案（技术依据 + 与既有决策/红线的一致性）
- 影响面：动了哪些文件/接口/数据，是否影响已拍板的其他决策
- 可回退性：被人类推翻时的返工面有多大
```

## 5. 验收与归档

1. **终验**：全量测试、静态检查、生产构建；涉及前端的必须实看渲染；涉及外部依赖的按需真环境集成与功能验收。发现问题 → 修复 → 重跑终验直至全绿，复验结果一并回写——验收闭环是验证闭环，不只是记录闭环；确实无法全绿的部分如实呈报并写入已知边界，不许静默降级。
2. **结果回写**：验收结论与发现的问题（修了什么、为什么、验证结果）写入设计文档「变更记录」，使其成为"设计＋验收"完整闭环；已知边界（本期不做的事）明确写入，不留悬案。
3. **呈报临时决策**：存在 DECISIONS_TEMP.md 时逐条呈报人类审查（决策点｜当时的选择与理由｜影响面），结论（维持/推翻）与补救记录并入变更记录，然后删除该文件。
4. **确认归档**：用户确认后，先逐条核对每个 STEP 回填区的偏差与现场记录、全部临时决策均已并入设计文档变更记录（核对是动作，不是断言），再迁移归档、删除计划目录下本项目全部执行期文档——保留执行期文档只会制造"到底完没完成"的歧义。**计划目录只装进行中的项目**：新接手者打开看到的应是一张白纸加一份宪法，不是历史悬案。

## 6. 宪法修订

宪法从实战教训中演进，不从纸面推演中加码。实战暴露宪法缺陷（规则真空、条款失效、表述误导）时：当场按"规则未覆盖的边界按理由外推"先行处置、不中断工作，并将缺陷与外推处置一并记入下次人类关口呈报；修订仅限两类——修真失效的条款、删被证伪的条款，禁止为假想场景新增条款；经用户确认后生效，动因记入提交信息。
