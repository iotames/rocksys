## 1. 真实痛点（现状 + 证据）

### 1.1 无任何数据迁移能力

RockSys 支持三方言（sqlite/mysql/postgres）运行库，但**换库、备份外迁、数据汇聚全靠手工导出导入**：

- 表同步（schema 同步）只作用于**运行库自身**：`GET /admin/db/schema` + `POST /admin/db/exec`（`internal/adminapi/dbschema.go:29-31`），期望结构来自运行期 SQLSource，无法对任意外部库执行。
- 数据层只有查询（表概览 `/admin/db/size`、SQL 历史 `/admin/db/execlog`），无跨库搬运入口。
- 换库场景（如开发 SQLite → 生产 MySQL）目前只能 mysqldump/sqlite3 .dump 等命令行工具手工拼，方言不通、无 UI、无进度。

### 1.2 地基库已备好多数据源底座，RockSys 未接入

`easydb/dsn`（`D:\projects\golang\rocksys\easydb\dsn\datasource.go`）已提供：

- `DsnGroup`：多数据源管理（增删、`ActiveCode`、按 `Name` 引用——`DataSource.Name` 注释明示「用于 ETL 任务按名引用」）；
- `dsn.DsnConf`（`dsn/conf.go`）：JSON 文件持久化（`GetDsnGroup`/`SaveDsnGroup`）；
- MySQL DSN 密码含 `@` 校验（`CheckMySQLDSNPassword`）。

RockSys 全仓无一处 import（rg `easydb/dsn` 零命中）——底座空转。

### 1.3 数据库页页签缺「数据」维度

`webui/assets/js/views/database.js:296`：页签仅 表同步（schema）/ 表概览（overview）/ SQL 历史（history），结构有了、体积有了，**数据本身无落脚点**。

### 1.4 GeoIP 同步卡错挂在「表概览」页签

GeoIP 同步卡（`database.js:420 geoSyncHTML`，`overviewHTML()` 末尾 `database.js:414` 挂载）语义是**数据维护工具**而非「表结构概览」，与页签主题不符；用户定调移入新「表数据」页签并更名「GeoIP 数据同步」。

## 2. 需求（本方案要达成的目标）

1. 数据库页新增「表数据」页签，顺序：表同步 → 表概览 → **表数据** → SQL 历史（用户指定）。
2. 数据源配置（底座 = `easydb/dsn`）：增删改查外部数据源（三方言驱动），连通测试，持久化。
3. 选定迁移目标后，**复用已有表同步链路**对目标库对齐表结构（三方言内嵌 SQL 源现成）。
4. 数据迁移（仿 Kettle 表输入→表输出模型）：同名字段跨方言直迁，默认 **1000 行/批**；批次大小存内存、可临时修改、**不持久化**（重启恢复默认 1000）。
5. GeoIP 同步卡移入「表数据」页签，更名「GeoIP 数据同步」（逻辑与端点不动）。
6. 通用 ETL 方案规划：模型上源/目标皆可为任意数据源，本期落地范围与边界明确（见 §4.7）。

## 4. 设计方案

### 4.0 数据结构与数据流（数据设计总览，宪法 §7）

> 本方案**无新增数据库表**：数据源是运行资产而非业务数据，存 JSON 文件（D11）；迁移任务状态存内存（D12）。故 `docs/DATA_DICT.md` 无变更，此处按宪法 §7 阐明文件型数据结构与全局配置项。

**全局配置项（easyconf 注册，唯一新增）**

- `CONF_DIR`：全局统一配置目录，字符串，默认 `conf`（相对工作目录，开发规范下即 `bin/conf/`）；经 `conf.Manager.Register` 注册（title/usage 注明目录语义与 `dsn.json` 位置），`default.env` 随装配自动同步。生效语义：每次读写数据源文件时**实时取 `CONF_DIR` 当前值**拼接路径（支持热更）；变更后原位置的 `dsn.json` **不自动搬迁**——需手工移动，否则按新位置视为全新空配置（已知边界，§8）。

**数据类型（`<CONF_DIR>/dsn.json`，由 `dsn.DsnConf` 序列化；懒创建——首次写入时目录/文件不存在则新建）**

```json
{
  "ActiveCode": "<md5(dsn)>",
  "DsnList": [
    { "Code": "<md5(dsn)>", "Name": "prod-mysql", "DriverName": "mysql", "Dsn": "user:pass@tcp(host:3306)/db" }
  ]
}
```

- `Code` = `md5(Dsn)`（`dsn` 包生成，唯一定位）；`Name` 人工连接名（唯一，迁移目标按名引用）；`DriverName` ∈ {sqlite, mysql, postgres}（须为已注册驱动）；`Dsn` 完整连接串（含密码，本机明文，UI 脱敏展示）；`ActiveCode` 由底座维护（首次追加自动激活），本方案按 Code/Name 引用、**不依赖激活态**。

**数据关系**：数据源 ↔ 迁移任务 = 按名/按 Code 引用（无外键，JSON 文件与内存任务解耦）；迁移目标库的表结构 ← 内嵌 SQL 源（与运行库表同步同源）。

**数据流转**：① CRUD 端点写 `<CONF_DIR>/dsn.json`（`SaveDsnGroup` 原子写：临时文件 + rename 替换，写中途崩溃不留半截文件）；② 表结构对齐：读运行库同款 SQLSource → 对目标库 diff → 生成 DDL → 目标库执行；③ 数据迁移：源库流式 SELECT → 内存攒批（默认 1000 行）→ 目标库事务批量 INSERT → 循环至游标尽；④ GeoIP 数据同步：数据流不变（现状 `geoSyncAll`）。

### 4.1 页面：「表数据」页签（`views/database.js`）

- `state.tab` 新增 `'data'`，页签顺序 `schema → overview → data → history`（`database.js:296` tabsHTML 数组插入）；`state.geo` 状态随卡迁入 data 页签。
- 页签内**自上而下按迁移流程排列**四卡（对应「先数据源配置 → 选迁移目标 → 结构对齐 → 数据迁移」）：
  1. **数据源**卡：列表（名称/类型/DSN 脱敏）+ 添加（名称、驱动下拉三方言、DSN、连通测试按钮）+ 删除；连通测试独立按钮（`POST /admin/db/dsn/test`，ping + 版本号回显）。
  2. **表结构对齐**卡：下拉选迁移目标（数据源之一）→「检查差异」（diff 项 + 生成 DDL 预览，复用表同步页的展示形态）→「执行对齐」（逐条执行、遇错停、结果回显；执行前确认弹窗）。
  3. **数据迁移**卡：源（默认「本机运行库」，可切数据源）+ 目标（数据源；**不可选运行库**，下拉中不出现）+ 表清单（多选，来源=期望结构业务表）+ 批次大小输入框（默认 1000，本次会话内存态，改后不落盘；输入框备注，D17：「默认 1000 行/批，性能参考值：批越大吞吐越高，内存占用与目标库单语句负载也越高；超出目标库参数上限时服务端自动切分执行，无需手工计算」）+ 冲突策略（清空重灌/跳过冲突）→「启动迁移」→ **表级进度区**（D12）：每张表一行——状态（待迁移/迁移中/已完成/失败/已取消）+ 行数进度（已迁/总）；**待迁移**状态的表带单表取消按钮（从本次任务移除）；另设整任务取消按钮（当前批次事务完成后停止）；全局互斥（有任务在跑时启动按钮禁用并提示）。
  4. **GeoIP 数据同步**卡：整卡自表概览页签移入（`geoSyncHTML` 调用点从 `overviewHTML()` 移至新 `dataHTML()`），标题「GeoIP 同步」→「GeoIP 数据同步」；按钮、确认弹窗、端点、断点续填逻辑零改动。
- UX 红线照旧：load fetch 透传 `opts`（含 `silent`）；非引导态失败弹 `Rock.ui.toast(msg,'error')` 不自动消失；文案三要素。

### 4.3 目标库表结构对齐（复用表同步链路）

- 复用点：`db.Open(targetDriver, targetDsn)`（`internal/db/db.go:108`）为**目标库**开 `*db.DB`——**不传 ScriptHub**：hub 对同名子目录只允许注册一次（`internal/hotswap/hub.go:101`，防装配缺陷的刻意设计），运行库启动时已注册 `sql/`，目标库再传同一 hub 必然 Open 失败；不传时 `DB.SQL()` 走 `ScriptDir` 直读（`internal/db/db.go:195`），读取语义与运行库**同源**（外挂优先、内嵌兜底，同一份内嵌 FS 与外挂目录），仅无缓存与热更订阅——对低频运维动作无影响。「同源」靠读同一份脚本文件达成，而非共享 hub 实例。`DiffSchema(ctx, targetDB, specs)` + `GenerateSQL`（`internal/db/schema_diff.go:236/381`）原样复用——现有链路本就按 `DB.driver` 分方言，目标库连接换入即用。
- `specs` 来源与运行库表同步一致（同 SQLSource 解析），**保证迁移双方结构同名同义**。

| 端点 | 方法 | 说明 |
|---|---|---|
| `/admin/db/migrate/schema` | GET | `?code=<数据源>`：目标库 diff 预览（items + 生成 DDL 文本，只读） |
| `/admin/db/migrate/schema_apply` | POST | `?code=`：对目标库逐条执行 DDL（拆句、遇错停、逐条结果回显——照 `/admin/db/exec` 模式）；**不写运行库 `sql_exec_log`**（D14：目标库动作不属于运行库审计域，结果在响应与任务进度展示） |

### 4.4 数据迁移执行器（`internal/adminapi/migrate.go` 新增）

- **执行模型**：后台 goroutine + 内存任务注册表（`sync.Mutex` 互斥，全局单任务）；context 取消支持；进度快照原子读。
- **读（表输入）**：源连接读 `SELECT * FROM <table>`（`rows.Next()` 逐行迭代、攒批即写，**应用层内存占用与表行数解耦**，只与批次大小相关；无 OFFSET 翻页、不依赖主键形态）；`rows.Columns()` 取源列名。注：PG/MySQL 协议下服务端仍会物化/推送完整结果集，超大表的源库侧影响见 §8 边界。
- **攒批（Kettle batch）**：累计 `batchSize` 行（默认 1000；请求参数临时传入，服务端 clamp 100–10000，内存态不落盘——D5）。
- **写（表输出）**：目标库**同名列**批量 `INSERT INTO t (col,…) VALUES (…),…`，每批一个事务（批次 = 事务粒度）；源有而目标无的列 → 报错终止该表并提示「先执行表结构对齐」；类型经 `database/sql` 原生传递（时间/字节/数值由驱动双方方言自适应，D6 同名字段直迁）。
- **占位符预算与切子批**（D17）：参数化 INSERT 的占位符数 = 列数 × 行数，三方言硬上限为 SQLite 32766、PG/MySQL 65535（协议 16 位计数），批次过大必撞限整批报错，且单纯下调批次上限治不了标（33 列 × 1000 行即超 SQLite）；执行器按预算常量 `migratePlaceholderBudget = 30000`（三方言通用、留余量）自适应切子批——子批行数 = 预算 ÷ 列数（至少 1 行），每子批一条参数化 INSERT、**共享同一事务**，事务边界/取消/进度语义不变，用户无感知。
- **自增序列重置**（D18）：每表数据迁完（done）后，将目标库该表自增序列重置为当前 max(id)——SQLite 更新 `sqlite_sequence`、MySQL `ALTER TABLE … AUTO_INCREMENT`、PG `setval`；仅对含整型自增主键的表执行，无自增主键的表（如 `geoip_list` 文本主键）自动跳过。缺失此步时换库后首批写入即主键冲突（目标库序列停在 0 或旧值）。
- **冲突策略**（D13）：`replace` = 写前清空目标表（MySQL/PG `TRUNCATE`、SQLite `DELETE FROM`）；`skip` = 冲突行跳过（MySQL `INSERT IGNORE`、SQLite/PG `ON CONFLICT DO NOTHING`）。
- **表级进度与取消**（D12）：启动时预查各表 `COUNT(*)`（粗总行数）；进度按表快照——每表 `{name, status: pending/running/done/failed/cancelled, rowsDone, rowsTotal, err, 起止时间}`；**单表取消**仅对 `pending` 状态生效（从任务队列移除），**整任务取消**= 当前批事务完成后停止、剩余表全部置 `cancelled`；单表失败**不中断**后续表（结果汇总回显，仿 Kettle 步骤级错误报告）。

| 端点 | 方法 | 说明 |
|---|---|---|
| `/admin/db/migrate/start` | POST | `{source:"self"\|"<dsnCode>", target:"<code>", tables:[…], batch:1000, mode:"replace"\|"skip"}`；校验目标≠运行库、任务互斥、表清单非空 |
| `/admin/db/migrate/status` | GET | 任务状态：idle/running/done/failed/cancelled + **表级明细数组**（每表状态/行数进度/错误） |
| `/admin/db/migrate/cancel` | POST | `{table?}`：带 `table` = 取消该**待迁移**表（仅 pending 可取消）；不带 = 取消整个任务（当前批事务完成后停止，已写入行保留——重跑即幂等续接） |

### 4.5 批次大小语义（D5/D17）

- 默认值 = 代码常量 `migrateDefaultBatch = 1000`；仅存于任务请求与任务内存态；UI 输入框默认填 1000、可改、刷新页面复位；**不注册 easyconf、不落任何文件**（明示边界：重启后一切恢复默认）。
- 批次是**事务粒度与性能参数**，其数值本身无撞限风险：单条 INSERT 的占位符上限由服务端按预算自动切子批兜底（D17），用户无需按表宽手工计算。

### 4.6 GeoIP 数据同步卡（D7）

- 位移 + 改名，零逻辑改动：`database.js` 中 `geoSyncHTML`/`runGeoSync`/`state.geo` 原样，仅挂载点与标题变；端点 `POST /admin/db/geoip_sync` 不动。
- 表概览页签移除该卡后恢复纯「空间占用/数据表概览」主题。
- 交叉锚点（D16）：GEOIP_LIST_PLAN（待定稿）的 D22/D31 所述「数据库页同步卡」最终位置即本页签此卡；两方案执行顺序由用户安排，其表述修订随用户安排进行，本方案不代改。

### 4.7 影响面清单

- **Go**：`internal/adminapi/dsn.go`（新，数据源 CRUD + 存储）、`internal/adminapi/migrate.go`（新，结构对齐 + 迁移执行器）、`internal/adminapi/adminapi.go`（路由注册）、`cmd/rocksys/main.go`（装配：`CONF_DIR` 注册；`main_test.go` 配置项断言清单同步加入 `CONF_DIR`）；对应 `_test.go`（dsn CRUD 单测、迁移执行器以 SQLite 双库真跑、批次 clamp 单测）。
- **依赖**：`easydb/dsn` 首次接入（地基库本地 replace，无外部新依赖）。
- **配置**：新增 `CONF_DIR`（easyconf 注册，默认 `conf`，见 §4.0）——本方案唯一新增配置项。
- **前端**：`views/database.js`（页签 + 四卡 + state 扩展）；无新 view 文件（同页内页签扩展）。
- **文档**：`docs/webui.md`（数据库页页签与操作说明）、`docs/webui-api.md`（新端点 9 个：dsn 4 + migrate 5）、`docs/CONFIGURATION.md`（`CONF_DIR`）、`README.md`（功能清单如提及）；`docs/DATA_DICT.md` **无变更**（无新表，见 §4.0）；`docs/plan/GEOIP_LIST_PLAN.md` D22/D31 表述修订时机由用户安排（D16），本方案仅留交叉锚点。

### 4.8 明确不做（边界）

- 不做源库结构克隆到目标库（D10：结构对齐=对齐 RockSys 内嵌期望结构；任意两外部库间结构克隆不做）；
- 不做字段映射/值转换规则（Kettle 的转换步骤域——同名字段直迁，D6）；
- 目标=运行库的迁移不做（D9，防误覆盖生产数据）；源/目标均为外部数据源的**数据**迁移支持（结构须已对齐或手工存在）；
- 不做任务持久化与断点续传落盘（D12：重启丢任务状态，重跑幂等续接——`replace` 重跑等价重来、`skip` 重跑自动跳过已写行）；
- 不做任务调度/定时迁移、并行多任务（全局单任务串行）；
- GeoIP 数据同步逻辑、端点、断点续填机制零改动（D7 位移不重写）。

## 5. 验收标准

1. 「表数据」页签按序落位（表同步→表概览→表数据→SQL历史）；GeoIP 卡在表数据页签内、标题「GeoIP 数据同步」、功能与现状一致（同步/断点续填/错误提示可用）；表概览页签不再含该卡。
2. 数据源管理：三方言 DSN 可增删查（DSN 脱敏展示）、连通测试返回版本；`<CONF_DIR>/dsn.json` 持久化且重启后保留（默认 `CONF_DIR=conf` 即 `bin/conf/dsn.json`，首次写入自动建目录与文件；改 `CONF_DIR` 后位置随生效值变化）；`Name` 重复、DSN 重复、未注册驱动、MySQL 密码裸 `@` 均被拦截并给出指引文案。
3. 表结构对齐：选目标库（三方言各验一）→ 检查差异与 DDL 预览正确 → 执行后目标库结构与运行库表同步结果一致（比对 diff 复检为空）；执行结果逐条回显，遇错停且可重试。
4. 数据迁移：SQLite→MySQL、MySQL→PG 至少各一真实双库用例——结构对齐后迁移，行数一致、抽样字段值一致（时间/字节/数值类型各覆盖）；批次 1000 默认生效，临时改批（如 7）行为正确且刷新后复位 1000；30 列以上宽表 × 10000 大批次不触发占位符上限报错（自适应切子批生效、数据完整）；`replace` 重灌与 `skip` 跳过冲突行为正确；**自增序列重置生效**（D18：迁移后向目标库补写一条新记录，主键 = max(id)+1 不冲突；无自增主键的表如 geoip_list 不受影响）；**表级进度实时可见**（每表状态与行数进度）、**单表取消**（仅待迁移表）与**整任务取消**生效；单表故意失败不阻塞后续表并汇总报错。
5. 互斥与防护：任务运行中再启动被拒并提示；目标=运行库被拒；运行中数据源不可删除。
6. `go build -tags dev` / `go vet ./...` / `go test ./...` 全绿；前端改动开浏览器实看并截图留证（含数据源 CRUD、结构对齐、迁移全程与表级进度/取消、GeoIP 卡新位置）。
7. 文档同步：webui.md / webui-api.md / CONFIGURATION.md（CONF_DIR）/ README.md 逐项核对更新。

## 6. 决策取舍与备选（讨论留痕）

|---|---|---|---|
| 迁移方向 | 仅运行库→外部 / 任意↔任意 | 通用模型 + 默认源=运行库（D9） | 主场景是换库迁移；通用模型只多一个源下拉，执行器本就面向任意连接；目标禁=运行库防误覆盖生产数据 |

| 分页方式 | OFFSET 翻页 / 主键游标 / 流式游标 | 流式游标 | 无 OFFSET 深翻页退化、不依赖主键形态；database/sql 三方言驱动天然支持 |

## 8. 验收结论与已知边界

> 本节待实施与终验后回填。

**已知边界（设计期已定，终验核对）**
- 迁移任务状态不持久化：服务重启后进行中任务的进度丢失，需重新发起（重跑幂等，无数据损坏风险）。
- 批次大小重启复位 1000（用户明示语义）。
- 源有而目标无的列触发该表失败（提示先结构对齐），不做自动建列。
- `<CONF_DIR>/dsn.json` 含 DSN 明文密码：本机文件与 `bin/.env` 同级安全边界，不入库不入 git（bin/ 已在忽略约定内）。
- `CONF_DIR` 变更后原位置 `dsn.json` 不自动搬迁（需手工移动，否则按新位置视为空配置）。
- 表清单来源=期望结构业务表：源库中不在期望结构的表不参与迁移（边界内语义，页面文案注明）。
- 源库读侧：应用层逐行流式（内存占用与表行数解耦），但 PG/MySQL 协议特性使服务端仍会物化/推送完整结果集——超大表迁移需评估源库侧内存与连接占用（本期不做游标式真流式与分页降级）。
